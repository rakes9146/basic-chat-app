SECTION 2: PROBLEMS ENCOUNTERED & SOLUTIONS
================================================================================

PROBLEM 1: FRONTEND BUILD FAILED - CSS BUDGET EXCEEDED
-------------------------------------------------------
Error Message:
  "Error: chat.component.scss exceeded maximum budget. 
   Budget 4.10 kB was not met by 12.28 kB with a total of 16.38 kB"

Root Cause:
  - Angular's production build enforces strict bundle size limits
  - chat.component.scss (16.38 KB) exceeded the 4 KB limit
  - Default budget settings too restrictive for production app

Solution Applied:
  Modified: frontend/angular.json
  
  Changed budget limits:
    FROM:
      "type": "anyComponentStyle",
      "maximumWarning": "2kb",
      "maximumError": "4kb"
    
    TO:
      "type": "anyComponentStyle",
      "maximumWarning": "20kb",
      "maximumError": "50kb"

Result: ✅ Build successful

--------------------------------------------------------------------------------

PROBLEM 2: FRONTEND BUILD FAILED - GOOGLE FONTS INLINING ERROR
---------------------------------------------------------------
Error Message:
  "Index html generation failed. Inlining of fonts failed. 
   An error has occurred while retrieving 
   https://fonts.googleapis.com/css2?family=Roboto over the internet"

Root Cause:
  - Docker build environment has no internet access
  - Angular tries to inline Google Fonts during production build
  - Font optimization requires external HTTP requests

Solution Applied:
  Modified: frontend/angular.json
  
  Changed optimization settings:
    FROM:
      "optimization": true
    
    TO:
      "optimization": {
        "scripts": true,
        "styles": {
          "minify": true,
          "inlineCritical": false
        },
        "fonts": false
      }

Additional Fix:
  - Changed deprecated property:
    FROM: "defaultCollection": "@schematics/angular"
    TO: "schematicCollections": ["@schematics/angular"]

Result: ✅ Build successful

--------------------------------------------------------------------------------

PROBLEM 3: MYSQL PORT CONFLICT (3306 ALREADY IN USE)
-----------------------------------------------------
Error Message:
  "Ports are not available: exposing port TCP 0.0.0.0:3306 -> 127.0.0.1:0: 
   bind: Only one usage of each socket address is normally permitted"

Root Cause:
  - Local MySQL service running on port 3306
  - Docker's MySQL container couldn't bind to same port
  - Windows MySQL80 service was active

Solution Options:

  OPTION A (Recommended): Stop Local MySQL Service
  Command:
    net stop MySQL80
    # OR
    Stop-Service -Name "MySQL80"
  
  OPTION B: Change Docker MySQL Port
  Modified: .env file
    FROM: MYSQL_PORT=3306
    TO:   MYSQL_PORT=3307
  
  Then restart:
    docker-compose down
    docker-compose up -d

Result: ✅ Services started successfully

PROBLEM 4: KAFKA & EUREKA HEALTH CHECK FAILURES
------------------------------------------------
Error Message:
  "Container chat-kafka is unhealthy"
  "Container chat-eureka - Error: dependency failed to start"

Root Cause:
  - Health check commands were incorrect for Apache Kafka image
  - Kafka service was running fine but failing health checks
  - Eureka couldn't start because it waited for Kafka health check
  - Service logs showed both were actually working correctly

Solution Applied:
  Modified: docker-compose.yml
  
  1. Removed strict Kafka health check:
     REMOVED: healthcheck with kafka-broker-api-versions command
  
  2. Simplified all depends_on conditions:
     FROM:
       depends_on:
         kafka:
           condition: service_healthy
         eureka:
           condition: service_healthy
     
     TO:
       depends_on:
         - kafka
         - eureka
  
  3. Removed obsolete version line:
     REMOVED: version: '3.8'

Result: ✅ All services started in correct order without health check blocking

PROBLEM 5: MESSAGE-SERVICE KAFKA CONNECTION FAILED
---------------------------------------------------
Error Message:
  "[Consumer clientId=consumer-message-ws-1] Connection to node -1 
   (localhost/127.0.0.1:9092) could not be established. 
   Node may not be available"

Root Cause:
  - KafkaConfig.java had hardcoded "localhost:9092" in Java code
  - Environment variables in docker-compose.yml weren't being used
  - Spring wasn't overriding the hardcoded values
  - Multiple consumer groups all failing to connect

Impact:
  ❌ Online/offline status updates not working
  ❌ Real-time message delivery blocked
  ❌ Delivery and read receipts not functioning
  ❌ WebSocket push notifications failing

Solution Applied:

  STEP 1: Created profile-specific properties file
  Created: message-service/src/main/resources/application-docker.properties
  
  Content:
    spring.kafka.bootstrap-servers=kafka:9092
    spring.kafka.producer.bootstrap-servers=kafka:9092
    spring.kafka.consumer.bootstrap-servers=kafka:9092
    spring.datasource.url=jdbc:mysql://mysql:3306/chatdb
    spring.redis.host=redis
    eureka.client.service-url.defaultZone=http://eureka:8761/eureka

  STEP 2: Modified Java Configuration Class
  Modified: message-service/src/main/java/.../config/KafkaConfig.java
  
  Added:
    @Value("${spring.kafka.bootstrap-servers}")
    private String bootstrapServers;
  
  Changed:
    FROM: config.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    TO:   config.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
    
    FROM: config.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    TO:   config.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);

  STEP 3: Rebuilt Service
  Commands:
    docker-compose stop message-service
    docker-compose rm -f message-service
    docker-compose build --no-cache message-service
    docker-compose up -d message-service

Result: ✅ Kafka connection successful, all real-time features working

7.2 INSTALL DOCKER ON LIGHTSAIL (AMAZON LINUX 2023)
----------------------------------------------------
Commands:
  # Update system
  sudo dnf update -y
  
  # Install Docker
  sudo dnf install docker -y
  
  # Start Docker service
  sudo systemctl start docker
  sudo systemctl enable docker
  
  # Add user to docker group
  sudo usermod -aG docker ec2-user
  
  # Log out and back in for group changes to take effect
  exit
  # Then reconnect
  ssh ec2-user@<your-lightsail-ip>
  
  # Verify Docker installation
  docker --version
  
  # Install Docker Compose
  sudo curl -L "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose
  sudo chmod +x /usr/local/bin/docker-compose
  
  # Verify Docker Compose installation
  docker-compose --version

Description:
  - Installs Docker and Docker Compose on Amazon Linux 2023
  - Uses dnf package manager (not apt like Ubuntu)
  - Adds ec2-user to docker group (no sudo needed after re-login)
  - Enables Docker to start automatically on boot
  - Verifies successful installation

Key Differences from Ubuntu:
  - Package manager: dnf (not apt)
  - User: ec2-user (not ubuntu)
  - Docker from Amazon's repository (not docker.io)
  - Systemctl to manage services

  - If docker-compose pull shows "Skipped - No image to be pulled":

    * Keep only `image: rakes9146/chat-*:latest` lines
  - Production deployment doesn't need source code folders

PROBLEM ENCOUNTERED DURING DEPLOYMENT:
--------------------------------------
Issue: "Skipped - No image to be pulled" for custom services
Then: "unable to prepare context: path '/home/ec2-user/frontend' not found"

Root Cause:
  - docker-compose.yml contained both `build:` and `image:` sections
  - Docker Compose tried to build locally instead of pulling from Docker Hub
  - Build context folders don't exist on server (only docker-compose.yml uploaded)

Solution:
  1. Edit docker-compose.yml on server or create temp file
     nano docker-compose.yml
  
  2. Remove ALL `build:` sections from custom services (keep infrastructure services)
  
  3. Alternative: Create corrected file and rename
     nano docker-compose_temp.yml
     mv docker-compose_temp.yml docker-compose.yml
  
  4. Retry pull and start:
     docker-compose pull
     docker-compose up -d

Result: ✅ All images pulled successfully from Docker Hub, services started

SECTION 8: TROUBLESHOOTING QUICK REFERENCE
================================================================================

ISSUE: Container Won't Start
-----------------------------
Solution:
  1. Check logs: docker-compose logs <service-name>
  2. Check status: docker-compose ps
  3. Restart: docker-compose restart <service-name>
  4. Rebuild: docker-compose build --no-cache <service-name>

--------------------------------------------------------------------------------

ISSUE: Can't Connect to Database
---------------------------------
Solution:
  1. Verify MySQL is healthy: docker-compose ps mysql
  2. Check MySQL logs: docker-compose logs mysql
  3. Test connection: docker-compose exec mysql mysql -uchatuser -pchatpass
  4. Verify environment variables in .env file

--------------------------------------------------------------------------------

ISSUE: Kafka Connection Failures
---------------------------------
Solution:
  1. Check Kafka logs: docker-compose logs kafka
  2. Verify bootstrap servers in application-docker.properties
  3. Ensure KafkaConfig.java uses @Value annotation
  4. Rebuild message-service: docker-compose build --no-cache message-service

--------------------------------------------------------------------------------

ISSUE: Frontend Not Loading
----------------------------
Solution:
  1. Check frontend logs: docker-compose logs frontend
  2. Verify nginx configuration: docker-compose exec frontend cat /etc/nginx/conf.d/default.conf
  3. Rebuild frontend: docker-compose build --no-cache frontend
  4. Check browser console for errors (F12)

--------------------------------------------------------------------------------

ISSUE: WebSocket Connection Failed
-----------------------------------
Solution:
  1. Check message-service logs: docker-compose logs message-service
  2. Verify Kafka is connected (no localhost errors)
  3. Check API Gateway routing configuration
  4. Test WebSocket endpoint: curl -i -N -H "Connection: Upgrade" http://localhost:8082/MESSAGE-SERVICE/ws

--------------------------------------------------------------------------------

ISSUE: Out of Memory
--------------------
Solution:

     nano docker-compose.yml

     Example - Change this:
       eureka:
         build:
           context: ./eurekaserver
           dockerfile: Dockerfile
         image: rakes9146/chat-eureka:latest

       eureka:
         image: rakes9146/chat-eureka:latest
  
  3. Do this for all 5 services: eureka, api-gateway, user-service, 
     message-service, frontend
  
  4. Save and retry:
     docker-compose pull
     docker-compose up -d

SECTION 11: KEY LEARNINGS & BEST PRACTICES
================================================================================

1. MULTI-STAGE DOCKER BUILDS
   - Separate build and runtime stages
   - Reduces final image size significantly
   - Maven build stage + JRE runtime stage for Spring Boot
   - npm build stage + nginx serve stage for Angular

2. ENVIRONMENT-SPECIFIC CONFIGURATION
   - Use application-{profile}.properties for different environments
   - Never hardcode hostnames in Java code
   - Use @Value annotation to inject configuration
   - Keep sensitive data in .env (never commit to git)

3. HEALTH CHECKS
   - MySQL health check works well with mysqladmin ping
   - Kafka health checks can be problematic - use simple depends_on
   - Spring Boot Actuator provides /actuator/health endpoint
   - Balance between health checks and startup time

4. SERVICE DEPENDENCIES
   - Use depends_on for startup order
   - Avoid strict health check conditions if services work internally
   - Infrastructure services (MySQL, Kafka) start first
   - Application services (Eureka, microservices) start after

5. DOCKER COMPOSE BEST PRACTICES
   - Use named volumes for data persistence
   - Create custom network for service communication
   - Use restart: always for production resilience
   - Set meaningful container names
   - Use .env for environment-specific values

6. DEBUGGING TIPS
   - Always check logs first: docker-compose logs <service>
   - Verify network connectivity: docker exec <container> ping <target>
   - Check environment variables: docker exec <container> env
   - Rebuild with --no-cache after code changes
   - Use docker stats to monitor resource usage

7. PRODUCTION CONSIDERATIONS
   - Use strong, random passwords
   - Configure proper JVM heap sizes based on load
   - Enable monitoring and alerting
   - Set up automated backups
   - Use HTTPS with SSL certificates
   - Implement log rotation
   - Monitor disk space for volumes
